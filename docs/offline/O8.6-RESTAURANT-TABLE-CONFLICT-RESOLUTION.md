# O8.6 same-table conflict

Status: **PASSED WITH LIMITATIONS**. The server records one review row and the API test passed. A manager did not decide a conflict on a native window.

## Behavior

When a second offline dine-in names a table that already has an open order, `apply_open_order` keeps both orders. The first stays on the table. The second is stored with status `REVIEW` and no table. `TableSessionConflict` keeps the idempotency key, both order ids, the originating device, the actor, the reason, and the original payload.

Sending that same event again returns the original conflict id. It does not insert another order. A changed payload for the same idempotency key still follows the existing idempotency conflict.

The sync result status is `awaiting_review`. The desktop batch is marked the same way, so the till does not treat the ticket as a generic failure to retry forever.

## Decisions

`POST /api/v1/orders/table-conflicts/{id}/resolve` allows:

- `separate`: the second order becomes takeaway and stays open. The bills are not merged.
- `reassign`: the second order moves to a free table.
- `void`: the second order is voided. A line that already has a payment is refused.

The opener cannot decide their own conflict. The deciding user must have the existing void permission and must be the signed-in user. A second decision on an already resolved row returns that row and does not apply again.

The Orders screen `TableConflictPanel` loads the list when the server is reachable. It offers separate and void. It does not yet collect a free table for reassign. While offline it says the list will load when the server is reachable. Both local tickets stay on their registers.

The API test covers one conflict, a duplicate upload, a cashier refusal, and a manager separate decision. It does not cover a paid line or a native click.
