## Why the menu was visible while the register tables were empty

`CheckoutPage` loads dishes through `refresh_products`, which writes `products`. The on-screen card was that row: O810 Grill, SKU `O810-GRILL`, 1800 cents.

`register_menu` and `register_floor` are written only by `finish_bootstrap` and `apply_catalogue_pull`. The React sync loop called `flush_sync` and never called `bootstrap_catalogue` or `pull_catalogue`. `bootstrap_state` had no row. `menu_cache` held a separate assembled modifier document and is not the dish list.

`BOOTSTRAP_INCOMPLETE` is returned when the snapshot status is incomplete, or when products, staff, or the capability snapshot are missing. The status chip previously said products or staff were missing even when the real gap was the uncommitted snapshot.

## What changed

`flush` now downloads the signed snapshot when no complete cursor exists, then pulls later pages. A failed first snapshot is reported and does not roll back a sale receipt. Menu and floor rows commit in the existing bootstrap transaction with the cursor.

The setup chip title uses the register's dataset sentence while setup is incomplete: product count, staff count, menu rows, floor rows, and whether the cursor is committed. After a complete snapshot the chip clears.

When `GET /api/v1/dining/floor` cannot reach the API, the floor screen reads `register_floor` for this terminal's store. Other-branch rows are left out. Live occupancy is not invented offline; stored tables are free until the server answers.

An open takeaway, dine-in, or delivery ticket is reloaded from `table_sessions` after restart. The restored cart line keeps the saved line id and the saved unit price.
