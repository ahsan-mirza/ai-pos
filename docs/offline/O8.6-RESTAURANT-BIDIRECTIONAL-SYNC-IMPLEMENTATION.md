# O8.6 restaurant bidirectional sync

Status: **PASSED WITH LIMITATIONS**. The menu and floor feed, and the separate upload result for a table conflict, are in the current source. A native register did not download a menu page or upload a restaurant ticket in this pass.

## Ownership

| Dataset | Authority | Scope |
| --- | --- | --- |
| Menu modifiers | Server | Tenant. A branch does not own a private copy of the modifier definition. |
| Floor and tables | Server | Branch. A pull for one store omits another store's floor. |
| Checkout settings | Server | Tenant settings, cached on the register. |
| Open orders and lines | Originating register until accepted | Branch. The server merges lines by id. |
| Cash sales | Existing sale queue | Branch. Card, QR, and pay-later stay unpaid offline. |

## Downstream

`bootstrap_service` datasets include `menu` and `floor`. The first page is a snapshot session. Later pages use the signed bootstrap cursor. A floor row for another branch is an `omit` change, not a copied table.

The desktop applies those pages in `Db::apply_catalogue_pull`. Menu rows go to `register_menu`. Floor rows go to `register_floor`. A floor payload for another store is skipped. The cursor advances in the same SQLite transaction as the rows. An order line keeps the price stored on that line. The pull does not rewrite sales.

`menu_cache` is still the live modifier document from `GET /api/v1/menu/register`. A failed refresh keeps the previous body.

## Upstream

Open orders upload as `open_order` on the existing sync queue. The desktop marks a batch `awaiting_review` when any result has that status. It does not mint a new idempotency key for the retry. Sale and return queue columns were not changed. Staff provisioning stays on `staff_provisioning`.
